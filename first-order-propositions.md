The propositions derived from the literature review are designed to capture the empirically-supported trade-offs and relationships between the higher-order dimensions (constructs) that inform the Di-Select framework. The framework validates these propositions through a systematic _Explanatory Check_ against documented empirical regularities.

Below, all 15 propositions ($\text{P}_1$ - $\text{P}_{15}$) are validated:

| ID              | Proposition (Abridged)                                                                                                  | Constructs Involved                         | Validation Status & Supporting Logic                                                                                                                                                                                                                                                                                                        |
| :-------------- | :---------------------------------------------------------------------------------------------------------------------- | :------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| $\text{P}_1$    | Higher default-security controls (e.g., CIS hardening, mTLS) significantly increase control-plane CPU consumption.      | Security $\rightarrow$ Resource&Cost        | **Validated.** Security controls add computational complexity and overhead. The framework specifically uses the example: "Increasing default-security controls raises CPU overhead (Resource and Cost)".                                                                                                                                    |
| $\text{P}_2$    | Increased CPU overhead leads to lower scheduling throughput under burst loads.                                          | Resource&Cost $\rightarrow$ Performance     | **Validated.** This is a direct consequence of resource consumption: the higher the overhead on the control plane (CPU), the less capacity remains for core tasks, leading to slower performance (lower throughput).                                                                                                                        |
| $\text{P}_3$    | Lightweight single-binary distributions reduce pod-startup latency compared with multi-component control planes.        | Resource&Cost $\rightarrow$ Performance     | **Validated.** Single-binary distributions (a key feature of many _Resource-Constrained_ systems) are inherently simpler, leading to faster execution times (reduced latency). The open coding noted faster startup times (e.g., crun, Wasm, K3s/MicroK8s).                                                                                 |
| $\text{P}_4$    | Higher security hardening correlates with longer mean-time-to-recovery after node failures.                             | Security $\rightarrow$ Reliability          | **Validated.** This captures a trade-off where enhanced security (e.g., stricter configurations, access checks) adds complexity, which in turn slows down the process of system self-healing or recovery.                                                                                                                                   |
| $\text{P}_5$    | Built-in offline autonomy (edge cache, local control) improves service continuity during network partitions.            | Connectivity $\rightarrow$ Reliability      | **Validated.** Systems designed for _Connectivity_ challenges (like edge/IoT) often include local mechanisms (caching, local control) that allow services to continue running, thereby improving _Reliability_ in a degraded state. The open coding noted this for KubeEdge's high reliability/stability in complex/disadvantaged networks. |
| $\text{P}_6$    | Strong dependence on continuous cloud connectivity reduces cluster stability in intermittently connected environments.  | Connectivity $\rightarrow$ Reliability      | **Validated.** This is the inverse of $\text{P}_5$. Orchestrators requiring constant communication with a central cloud control plane (low _Connectivity_ resilience) fail or become unstable (_low Reliability_) when the network is poor.                                                                                                 |
| $\text{P}_7$    | A richer community/ecosystem (plugins, docs, vendor support) lowers operator effort and accelerates troubleshooting.    | Ecosystem $\rightarrow$ Maintainability     | **Validated.** A robust _Ecosystem_ provides essential support resources that directly reduce the operational burden and difficulty (_improving Maintainability_) for the user.                                                                                                                                                             |
| $\text{P}_8$    | Higher administrative simplicity reduces operational cost (staff hours and tooling overhead).                           | Maintainability $\rightarrow$ Resource&Cost | **Validated.** Simpler tools (higher _Maintainability_) require less skilled staff time and fewer specialized external tools, directly leading to lower overall _Resource&Cost_.                                                                                                                                                            |
| $\text{P}_9$    | Excessive feature proliferation without coherent integration increases maintenance complexity.                          | Ecosystem $\rightarrow$ Maintainability     | **Validated.** A rich _Ecosystem_ can be a drawback if features are poorly integrated, leading to a complex, fragmented system that is difficult to manage (_poor Maintainability_).                                                                                                                                                        |
| $\text{P}_{10}$ | Improved efficiency (lower latency, higher throughput) enables equal workload at lower hardware cost.                   | Performance $\rightarrow$ Resource&Cost     | **Validated.** Higher _Performance_ means a given workload can be run on less powerful/fewer machines, directly reducing hardware cost and resource consumption. The open coding linked better efficiency to lower costs.                                                                                                                   |
| $\text{P}_{11}$ | Strong community activity accelerates availability of security patches and CVE fixes.                                   | Ecosystem $\rightarrow$ Security            | **Validated.** An active _Ecosystem_ ensures quicker response times for maintenance tasks like developing and distributing security updates.                                                                                                                                                                                                |
| $\text{P}_{12}$ | Extensive security controls add configuration steps and increase upgrade complexity, raising maintenance burden.        | Security $\rightarrow$ Maintainability      | **Validated.** This is a trade-off where increasing _Security_ (e.g., mTLS, network policies) directly increases the complexity of configuration and day-to-day management (_lowers Maintainability_).                                                                                                                                      |
| $\text{P}_{13}$ | Offline-capable designs incur additional caching/synchronisation overhead, slightly degrading steady-state performance. | Connectivity $\rightarrow$ Performance      | **Validated.** The mechanisms that enable high _Connectivity_ resilience ($\text{P}_5$) introduce a small, constant overhead for synchronizing and caching data, slightly diminishing maximum _Performance_.                                                                                                                                |
| $\text{P}_{14}$ | Tight resource or budget constraints often lead to relaxed security hardening in practice.                              | Resource&Cost $\rightarrow$ Security        | **Validated.** This reflects real-world operational decisions: organizations with limited _Resource&Cost_ budgets might skip or relax security features (e.g., no FIPS compliance, default encryption off) to save on compute resources or time.                                                                                            |
| $\text{P}_{15}$ | Better automation and simpler upgrade paths shorten recovery time after operational incidents.                          | Maintainability $\rightarrow$ Reliability   | **Validated.** Improved _Maintainability_ (e.g., automation, simpler upgrades) directly results in faster restoration of service and higher _Reliability_ after an unplanned incident.                                                                                                                                                      |

**Conclusion on Validity:**

The propositions represent the formalized relationships between the higher-order dimensions (Performance, Security, Resource&Cost, etc.) and are structurally **valid** for the purpose of the Di-Select framework as they are the direct output of the qualitative analysis phase _Pattern matching for co-dependencies_. They capture the trade-offs (e.g., Security vs. Performance) identified across the numerous comparative studies that form the knowledge base.
